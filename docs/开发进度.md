## 2. 已完成并验证的功能

### 采集端（`src/NetPeek.Collector`）

- **ETW 会话**（`Sources/EtwSnapshotSource.cs`）：会话名 `NetPeek.Collector`，订阅 `KernelTraceEventParser.Keywords.NetworkTCPIP`，覆盖 TCP/UDP 的 IPv4+IPv6 收发与重传。启动时清理残留同名会话。
- **归因规则**：统一读 payload PID（TraceEvent 已在 `FixupData` 把 payload PID 写回 `data.ProcessID`）；**刻意不订阅 Event ID 18**（`TcpIpTCPCopy`），否则下载量翻倍；重传单独累计，不混入上传量。
- **PID 复用处理**：进程身份键 = PID + 进程启动时间，检测到复用则清零重计。进程退出且连续 30 帧无流量后从字典移除。
- **命名管道服务端**（`Ipc/SnapshotPipeServer.cs`）：`\\.\pipe\NetPeekCollector`，`PipeDirection.Out` 单向，帧格式 = 4 字节小端长度 + UTF-8 JSON，1000ms 一帧。客户端断开后自动回到监听。
- **反向控制通道**（`Ipc/SnapshotControlServer.cs`，新增）：`\\.\pipe\NetPeekCollectorControl`，`PipeDirection.In`。命令为单行 UTF-8 文本 `pause` / `resume` / `toggle`（不区分大小写）。UI 每发一条命令建一次短连接，写完即断。
- **暂停语义**：`ISnapshotSource` 增加 `Pause()` / `Resume()` / `IsPaused`。暂停时 ETW 回调内 `Add`/`AddRetransmit` 直接短路（不再累计），`GetSnapshot()` 上报 `Status="paused"`、速率为 0，且**不推进 `LastTotal`**，因此累计值冻结、恢复后增量从冻结点继续（不会出现恢复瞬间的巨大尖峰）。

## 5. 关键实现说明与踩过的坑

**必须用 payload PID。** 事件头 PID 在内核网络事件里往往是接收中断所在的任意进程，不是流量归属方。TraceEvent 的 `KernelTraceEventParser` 已在内部把 payload PID 写回 `data.ProcessID`，所以直接读它即可。

**Event ID 18（`TcpIpTCPCopy`）不能累加。** 它和 `Data received` 是同一批数据的两次观察，订阅了下载量会翻倍。代码里刻意没有挂这个回调，改动时不要"顺手补全"。

**TraceEvent 3.2.6 的类名拼写错误。** IPv6 UDP 事件的数据类叫 `UpdIpV6TraceData`（`Udp` 拼成了 `Upd`），不是笔误，照抄即可。

**`PipeDirection.Out` 的管道无法反向使用**，所以暂停命令走的是独立的第二条控制管道，而不是复用快照管道。

**Rust 侧不要引 `windows-sys` 去调 `CreateFileW`。** 试过，`CreateFileW` 被 `Win32_Security` feature 门控、`ReadFile` 在 `Win32_System_IO`、`GENERIC_READ` 在 `Win32::Foundation`，feature 组合很折腾。`std::fs::File::open` 在 Windows 上本身就是 `CreateFileW` + `OPEN_EXISTING`，对命名管道路径直接可用。

**`cargo build` 报 `failed to remove netpeek-app.exe: 拒绝访问 (os error 5)`** 是上一次运行的实例还占着文件：`taskkill //F //IM netpeek-app.exe`。

**UI 不要以管理员运行。** Windows UIPI 会阻止 UI Automation 访问提权进程，界面就没法用自动化工具验证了。用 `explorer.exe <exe路径>` 可以从提权终端启出普通权限进程。采集服务反过来必须提权。

**PowerShell 脚本必须存成 UTF-8 带 BOM。** 无 BOM 时 Windows PowerShell 5.1 按 GBK 解码源文件，

## 7. 阶段 1 补验（2026-09-04，`scripts/verify-etw-scenarios.ps1`）

新增自动化验证脚本，覆盖技术选型第 12 节中可在本机自动跑的场景，**8 项全部通过**：

- **S1 连续 10 次 curl 短连接**（每次独立 TCP 连接，共 50MB）：累加 4 帧下载字节 ≈ 50.5MB，`EventsLost=0` → 短连接归因完整、不丢事件。
- **S2 进程快速退出**：短命 curl 下载 5MB 后立即退出，退出后条目仍保留（30 帧剪枝前），字节完整归因（5MB/5MB）。
- **S3 UDP 报文**（QUIC 同类 UDP 通道）：UdpClient 发 50×1KB 报文，按 sender PID 断言累计上传 50KB/50KB → UDP 归因完整。
- **S4 与第二个 ETW 会话并存**：logman 再开一个 Kernel-Network 实时会话（GUID `{7DD42A49-5329-4832-8DFD-43D979094A9B}`，0x10），并存期间下载 5.4MB 归因完整、`EventsLost=0`、会话可正常删除。

**关键发现（产品行为）**：存活时间短于快照周期（1s）的短命进程，**字节归因完整，但进程名解析失败（Name=""）**——快照线程每秒查一次 `ProcessMetadataCache`，进程已退出时拿不到名字。UI 已有兜底：空名进程在表格中显示「(系统/未归因)」（main.js:524、563），归因覆盖率只统计有名进程。数据不丢，属预期行为，不需要改采集逻辑。

**脚本要点**（踩坑记录）：
- 断言语义：短连接/并存场景**按 `TotalDownloadBytes` 逐帧累加**断言，不能用「DownloadTotal 总和增量」——后者会被 30 帧剪枝的旧进程条目抵消（套件跑久后旧 curl 条目被剪掉，总和反而下降）。
- 快速退出的短命进程断言**按新 PID 条目**（不在 base 帧 PID 集合中）查找，不能按 `Name -like 'curl*'`（Name 为空）。
- PowerShell 的 `BinaryReader.Dispose()` 会关闭底层管道流：`Read-Snapshot` 每次新建 reader 必须传 `leaveOpen: $true`，否则读一帧后管道被关，后续帧报 "Cannot access a closed pipe"。
- `logman create trace` 会话名带时间戳（`netpeek-coexist-HHmmss`），避免上一次失败运行残留的同名会话导致 create 失败。
- 函数名不能用 `Rd`（PowerShell 内置别名 `rd`=Remove-Item，会覆盖函数定义）。

验证脚本用法：`pwsh -ExecutionPolicy Bypass -File scripts\verify-etw-scenarios.ps1`（需采集服务已管理员运行；本地 HTTP 服务脚本自动起/复用 18081 端口）。

## 8. 阶段 5 打包（2026-09-04）

### 8.1 机制

- **采集服务 self-contained 单文件**：`scripts/build-installer.ps1` 先 `dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true` 产出 71MB 单文件 exe（LocalSystem 服务不依赖用户装 .NET 运行时）。
- **WiX fragment 合并**（`src/NetPeek.App/src-tauri/installer/collector.wxs`）：Tauri 生成的主 wxs 里 `DirectoryRef Id="INSTALLDIR"` 下加 `collector` 子目录，`Component` 装 `NetPeek.Collector.exe` 并挂 `ServiceInstall`（`Account="LocalSystem" Start="auto" Type="ownProcess"`）+ `ServiceControl`（`Stop="both" Remove="uninstall" Wait="yes"`）。`tauri.conf.json` 的 `bundle.windows.wix.fragmentPaths` + `componentGroupRefs` 把 fragment 并进 MSI。
- **Tauri 内置**：WebView2 检测（RegistrySearch `{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}` + downloadBootstrapper CustomAction）、MajorUpgrade 升级清理（UpgradeCode 稳定即可）、perMachine 安装范围。

### 8.2 实测结果

- **构建**：`pwsh -File scripts/build-installer.ps1` 产出 `NetPeek_0.1.0_x64_en-US.msi`（浮岛改版后 34.0MB）。
  MSI 的 File 表里两个文件都在：`netpeek-app.exe` 11.0MB + `NetPeek.Collector.exe` 74.6MB（未压缩），
  说明 collector.wxs 的 fragment 合并生效。
- **安装**：`msiexec /i` 后服务 `NetPeek.Collector` 为 Running/Automatic（LocalSystem），文件落 `C:\Program Files\NetPeek\`（netpeek-app.exe + collector\NetPeek.Collector.exe），管道快照 `status=ok EventsLost=0`。
- **升级**：版本号临时升 0.1.1 重装验证 MajorUpgrade——产品记录干净替换为单条 0.1.1、旧 0.1.0 移除、服务保持 Running/Automatic、快照正常。
- **卸载**：`msiexec /x` 后服务移除、`C:\Program Files\NetPeek\` 清空。

### 8.3 踩坑

- **Git Bash 会把 msiexec 的 `/i` `/x` `/qn` 参数改写**：MSYS 路径转换把 `/i` 变 `I:/`、`/qn` 变 `C:/Program Files/Git/qn`，msiexec 收到乱参数后挂起（CPU 0、永不退出）。**必须用 PowerShell 的 `Start-Process -ArgumentList @("/i","...msi","/qn",...)` 数组传参**，或 `MSYS_NO_PATHCONV=1` 前缀，不要直接从 Git Bash 调 msiexec。
- **WiX 相对 Source 路径解析点是 light 的 cwd**（`target/release/wix/x64`），而 Tauri bundler 每次先 `remove_dir_all` 清空该目录——所以 collector.wxs 的 `File Source` 不能用 `collector\NetPeek.Collector.exe`（会被清掉报 LGHT0103），改用 `..\..\NetPeek.Collector.exe` 指到 `target/release/`（不被清空），构建脚本把 exe 复制到那里。
- **fragment 里不要用 `$(var.Win64)`**：该变量只在 main.wxs 定义，fragment 单独 candle 时报 CNDL0150；硬编码 `Win64="yes"` 即可。
- **DisplayName/Description 用 ASCII**：中文会触发 LGHT0311（code page 1252）编码错误。
- **卸载日志尾部出现 `MainEngineThread is returning 1605`**（ERROR_UNKNOWN_PRODUCT）通常是同一条复合命令重复调了两次 `/x`（第二次产品已不存在）；以可观察状态（服务没了、文件没了）为准确认卸载成功。

- **代码签名**：需要证书，当前无，发布前用 Authenticode 签名 netpeek-app.exe 与 NetPeek.Collector.exe（及 MSI）。
- **人工验收**：休眠恢复、Windows 10 22H2 覆盖、浏览器真实大文件下载归因——需有对应环境或人工操作，无法在本机自动跑。

### 9.4 验收方法与查出来的实际缺陷

用一个临时的 `window.__TAURI__` 假桥接在普通浏览器里渲染四屏，headless Chrome + CDP 把视口锁死
1180×720 截图，交给 judge 子代理逐屏看。**脚手架（`ui/_preview*.js|html`、`.preview-shots/`）验收完已删除**
——`tauri.conf.json` 的 `frontendDist` 指向整个 `ui/` 目录，留在那里会被打进安装包。
未被引用的 `ui/vendor/uPlot.*` 也一并删了（图表是自己用 canvas 画的，charts.js 开头写了为什么不用 uPlot）。

这一轮真正查出来的代码缺陷：

- **实时折线图长期画成虚线**。`dashFrom` 约定「从这个下标起转虚线（暂停态）」，未暂停时 main.js 传 `-1`，
  charts.js 只判了 `typeof === 'number'`，于是实线段 `to <= from` 直接返回、虚线段从 -1 画到末尾——
  整条曲线都是虚线，等于界面一直在说「已暂停」。
- **顶栏「今日合计」的单位被裁掉**。顶栏是 `auto 1fr auto` 三列，实时屏多了视图胶囊和搜索框，
  左组放不下就把尾巴裁在岛外，只剩一个没有单位的数。改成左组 `flex:none`、第三列 `minmax(0,auto)`、
  搜索框 `flex: 0 1 240px; min-width: 132px`——窗口挤的时候先让搜索变窄。
- **`[hidden]` 被组件样式盖掉**。界面里绝大多数容器自带 `display:flex/grid`，会覆盖 UA 的 `[hidden]{display:none}`，
  结果外观屏底下叠着历史屏。加一条全局 `[hidden] { display: none !important; }` 放在所有组件规则之前。
- **数据岛的隐式 auto 行被 10 行表格顶到 392px**，把图和表一起挤出 250px 高的岛外；
  `.data-live` 必须显式写 `grid-template-rows: minmax(0, 1fr)`。
- **y 轴标注被裁成「00 MB/s」**。52px 的 y 轴槽在 11px 等宽下只放得下约 6 个字符，
  界面里的「10.00 MB/s」右对齐后从左边被切掉前几位。charts.js 另开一套坐标专用的紧凑格式（`axisBytes` / `axisRate`）。
- **归因覆盖率用了琥珀色**。琥珀是下载的专属语义（§1.2），改回正文色；
  它的点点下划线在 12px 下会和「已归因」糊成一条实线，加了 `text-underline-offset: 3px`。
- **排行行被 flex 压扁**。列向 flex 里的行默认可压缩，8 行 32px 塞进 130px 的槽会一起被压成 18px，
  图标连带被挤扁、列表永远不滚动；`.rank-row` 要 `flex: none`。没有真实图标时退回首字母牌，
  空的灰方块会在行首读成一条竖色条（§3.7 禁止项）。
- **滚动条用系统经典样式**，在暗色岛屿里画出亮灰滑块和上下箭头按钮。改成 `::-webkit-scrollbar` 自绘；

- **设置屏「采集服务」列只有说明、没有可操作项**，下三分之一空着。补了暂停/恢复采集
  （复用 `send_control_command`，走控制管道），措辞与顶栏状态胶囊统一成「监控中 / 已暂停 / 异常」——

## 15. 能量球「能量感」（2026-09-11 第二轮）

用户反馈修完贴边后「还是没有能量球的感觉」——几何对了，但球是死的：黑底 + 两段弧 +
一圈 10% 透明静态光，有流量时也没有任何视觉响应。本轮加一套分层光效系统，让球
「活」起来。改动：`ui/mini.html`（3 个光效层）、`ui/mini.css`（光效主体）、
`ui/mini.js`（能量强度驱动）。

### 15.1 设计：强度单一变量，分层各管一事

JS 每帧把「当前速率 ÷ 近 60 秒峰值」的加权和（下载 0.75 + 上传 0.35，钳到 1）写进
`.orb` 的 `--e`（0..1）；CSS 用 `calc(var(--e))` 换算各层透明度，1Hz 的阶跃输入经
700ms 过渡变成连续呼吸。颜色全部 `color-mix` 出自 `--down` / `--up`，主题换色光效跟走。

三层光效（DOM 顺序 = 叠放顺序，全部 pointer-events:none）：

1. **halo 球缘光环**：径向渐变只外扩 5px（窗口四边各留 8px，永不被裁出硬边）；
   `::after` 叠一层随负载增强的 box-shadow 外晕。自带 3.6s 的 scale 呼吸动画
   —— **透明度归强度管、呼吸只动 transform**，两个属性不打架。
2. **core 球心光斑**：径向渐变（中心偏上 38%），有流量时核心亮起来，
   像里面真的有东西在烧；数值加同色底纹阴影防止亮核吃掉笔画。
3. **sheen 旋转高光叶**：30° conic 高光绕球 7s 一圈，静默时唯一动的东西
   —— 零流量时球也是活的。

另加：数据弧 drop-shadow 同色发光（从「画上去的线」变「发出来的光」）。

### 15.2 状态语义

- **暂停**（§2.8 定格）：JS 停止更新 `--e`，光效停在最后一帧；呼吸/光叶放慢一档
  —— 读作「能量还在、被按住」，不是死机。
- **断连**：`is-offline` 类 —— 光叶和呼吸全停，只留 0.22 的暗淡轮廓；
  首帧快照到达前也按断连处理（不亮光效，等数据来了再「通电」）。
- `prefers-reduced-motion: reduce` 时呼吸/光叶动画全停，强度照常跟随流量。
- 动画只有 transform/opacity 两种（合成器直出，零重绘），常驻小窗开销可忽略。

### 15.3 验证

- `node --check` 通过；headless 逐状态截图（深色底 RGBA `101418FF` 模拟桌面）：
  live 满载（核心亮 + 球缘光晕 + 外溢光）、idle（暗盘余烬 + 可见表盘轨道）、
  paused（虚线定格 + 光效保留）、offline（只剩轮廓）。

  会得到纯红页面），费了两张图才对上。

### 17.1 采集端日志体系（新增，最高优先级）

**根因**：采集服务跑在 LocalSystem 下，`Host.CreateApplicationBuilder` 的默认
日志 provider 是 Console / EventSource / Debug —— 作为 Windows 服务运行时
Console 无处可去，等于没有日志。界面侧看不到服务的任何输出，服务崩了只会表现为
「管道断开」，无从判断原因。另外 `BackgroundService` 逃出去的异常会命中 .NET 默认
策略（`BackgroundServiceExceptionBehavior.StopHost`）直接停掉整个 Host，
而 `CollectorService` 当时只 catch 了 `IOException`。

**改动**：

- `src/NetPeek.Collector/Logging/CollectorLog.cs`（新）：
  - `%ProgramData%\NetPeek\collector.log`，2 MB 轮转、保留 2 份归档；
  - 选 ProgramData 是因为它默认允许 Users 读取，界面进程（普通用户令牌）
    无需提权即可打开；
  - 目录创建 / 轮转 / 写入全部吞异常 —— 日志自身绝不能成为故障源；
  - 同一文件里的 `FileLoggerProvider` 把现有 `ILogger` 调用桥接进来，
    采集端原有的 `_logger.LogError(...)` 一处没改就全部落盘。
- `Program.cs`：`AppDomain.UnhandledException` +
  `TaskScheduler.UnobservedTaskException` 两个钩子（后者要 `SetObserved()`，
  否则会升级成进程级崩溃），加启动横幅（pid / 用户 / 日志路径）。
- `CollectorService.cs`：补通用 `catch (Exception)`，把 StopHost 这条路堵死。
- `EtwSnapshotSource.cs`：事件线程原先裸调 `session.Source.Process()`，
  线程级未捕获异常同样直接崩进程；改为经 `ProcessEvents()` 包装并记录。
- Rust 侧新增 `collector_log_path` / `open_collector_log` 两个命令，
  设置屏「采集服务」列加「查看日志」按钮（explorer `/select` 高亮文件）。

### 17.2 设置越界修正 sanitize()（参考 Sniffnet conf.rs）

`merged_with_defaults` 只保证「字段存在、类型大致对」，不保证取值合理。
手工把 `settings.json` 改成 `retentionDays = -5`，prune 会算出未来的 cutoff
从而清空全部历史；改成 99999 则每次清理都做一次无意义的全表扫描。

新增 `sanitize()`：`rateUnit` 白名单（未知退回 auto）、`retentionDays` 限定
`[0, 3650]`（**0 = 永久保留必须放行**）、提醒阈值限定非有限值/负数/超上限归零、
布尔项类型校验。非法值一律「退回默认」而不是钳到边界 —— 用户意图已经不可靠时，
猜不如给个安全值。

合并与修正都收口在 `merged_with_defaults`，`init` / `load_settings` /
`save_settings` 三条路径共享同一套规则（`save_settings` 也走这套，
顺带挡住绕过界面直接 invoke 传越界值的路径）。

### 17.3 bogon 保留地址判定（参考 Sniffnet bogon.rs）

### 17.4 格式化截断 + 顺带修 fmtRate 缺档

## 18. Sniffnet 第三轮：按序修复 1–5（2026-09-12）

### 18.1 内嵌 SVG 旗帜——国旗在 Windows 上一直是失效的

**根因（上一轮我判断错了）**：Windows 的 Segoe UI Emoji 故意不含国旗字形
（微软为规避政治争议），区域指示符对（U+1F1E6–U+1F1FF）在 Windows 上恒渲染成两个字母。
浏览器、WebView2、Electron 一律如此，换 polyfill 字体也不可靠。
也就是说 `flagOf()` 产出的东西**对所有 Windows 用户都是失效的**，
而上一轮我看到「JP」还判成「headless 缺字体，真机正常」。

**做法**：`scripts/gen-flags.mjs`（一次性构建工具）下载 flag-icons 7.2.3（MIT），
把 270 面 4x3 SVG 用 resvg **栅格化成一张 512x408 的雪碧图**
（`ui/flags.png` 112 KB），再生成索引 `ui/flags.js`（4.7 KB）。

为什么不直接内嵌 SVG：270 个 SVG 合计 **2.0 MB**（塞尔维亚一面就 184 KB，全是国徽路径），
而显示尺寸只有 16x12 逻辑像素——那些细节一个像素都落不下去。栅格化后整包 117 KB。

**语义图标**：5 个内联 SVG（本机 / 局域网 / 组播 / 保留 / 未知），走 `currentColor`
跟随主题，对应 Sniffnet `country_utils` 的降级链。`bogonLabel` 的文本前缀保留
（「局域网 192.168.1.1 · SMB」）——图标分不出局域网和链路本地，文字不会丢信息。

**踩到的坑**：git-bash 的 GNU tar 把 `D:\...` 当转义序列解析，从 Node 传绝对路径
直接 fatal(2)；一律改用相对路径 + `cwd`。

**写测试时挖出的真 bug**：`peerIconNode` 对「形状合法但雪碧图没有」的码（DB-IP 的 `ZZ`）
返回 null，格子里既没旗也没图标，看着像渲染失败。改为退化成「未知」地球。

### 18.2 MMDB 运行时可换

内嵌库「发版即冻结」：DB-IP 每月更新，装了旧版的用户永远停在构建那天的数据。

- `geo.rs` 改 `Db` 枚举（内嵌 `Reader<&'static [u8]>` / 外部 `Reader<Vec<u8>>` /

  「所有对端突然都变成未知」），这条有专门的单测；
- 设置项 `countryDbPath`（空 = 内嵌）；`sanitize` 只校验类型，**不校验文件存在**——
  路径可能指向还没插上的移动硬盘，悄悄清空会让用户下次还得重填；

## 19. 小窗边框与球体 3D 材质修复（2026-09-12）

用户反馈三条：悬浮面板**外面有一层边框**；悬浮球**周围有透明边框**、**没有 3D 感**。
三条都不是观感分歧，真机取证后查到 **5 个相互独立**的缺陷，全部修掉并复验。

### 19.1 取证方法（本轮新建，可复用）

透明窗口的问题肉眼看不出量，必须上工具：

| 工具 | 作用 |
| --- | --- |
| CDP `screenshotAlpha()` | `Emulation.setDefaultBackgroundColorOverride` 设全透明再截图，拿到**带 alpha 通道**的 PNG。普通截图底色不透明，分不清「网页真的画了这圈」还是「浏览器补的底」 |
| `px2.py` / `px3.py` | 逐像素读 alpha：环扫描（圆心向外每环最大 alpha + 该点颜色）、四边/四角剖面、alpha 分桶。**alpha=6 这种肉眼绝对看不见的量就是这么量出来的** |
| `winprobe.py` | 窗口样式位 + `DwmGetWindowAttribute` 扩展帧边界 + NCRENDERING 等属性。用来分离「网页画的」和「系统画的」 |

**前提**：量窗口尺寸前必须 `shcore.SetProcessDpiAwareness(2)`。本机 1920×1200 @144 DPI
(150%)，非 DPI-aware 进程拿到的是缩放后的虚拟坐标（162 的窗口报成 108、屏幕报成
1280×800），和 CDP 的 `innerWidth` 对不上，据此会推出完全错误的结论。

### 19.2 五个根因

| # | 现象 | 根因 | 实测证据 |
| --- | --- | --- | --- |
| 1 | 面板外面一层边框 | 窗口带着 `WS_CAPTION\|WS_BORDER\|WS_SYSMENU\|WS_EX_WINDOWEDGE`，DWM 非客户区渲染开启，四周画出 9px 非客户区 | 窗口 184×175 vs DWM 扩展帧 166×166（左9 上0 右9 下9）；`NCRENDERING_ENABLED=1` |
| 2 | 面板同样有边框感 | `.panel{inset:0}` 与窗口同尺寸 → `box-shadow` 全部落在窗口外被裁；反过来**圆角外的四角被自身的投影填了色** | alpha 图 100% 非透明；左上角 alpha 12~23、左下 27~42（第二层阴影向下偏 6px） |
| 3 | 球周围透明边框 | 光晕是圆、窗口是方。halo 外扩 5px，`::after` 的 `box-shadow 0 0 16px 3px` 让半径扩散到 **70**，而窗口半宽只有 **54** | 环扫描 r=70→80 全是 `rgba(237,146,55)` alpha 17→6；窗口四边中段 alpha 2~9、**四角为 0** → 读作方框 |
| 4 | 首开球偏 | 首次显示时窗口被撑宽（逻辑 135 而非 108），切一次形态才被 `set_mini_shape` 纠正 | CDP 视口：首开 135×108 → 面板 → 收回 108×108 |
| 5 | 球无 3D 感 | 确实没有球面光照：`background:none`（纯色）、`boxShadow` 只有向外的光、`hasInsetShadow:false` | 只有「纯色圆 + 1px 描边 + 向外发光 + 球心亮斑 + 旋转扇形」，缺边缘暗化 / 镜面高光 / 球面明暗 |

**根因 1 的来源是 tao**（`tao-0.35.3/src/platform_impl/windows/window_state.rs:466`）：

```rust
pub fn undecorated_with_shadows(&self) -> bool {
    self.contains(WindowFlags::MARKER_UNDECORATED_SHADOW)   // = Tauri 的 shadow（默认 true）
        && !self.contains(WindowFlags::MARKER_DECORATIONS)  // = decorations:false
}
```

创建时 `window.rs:1238` 会 `w += insets.left+right; h += insets.top+bottom`，
insets 由 `calculate_insets_for_dpi()` 算（= `SM_CXSIZEFRAME + SM_CXPADDEDBORDER`）。
**即 `decorations:false` 并没有真的去掉边框**，它只是把边框交给 DWM 画。
另外 `to_window_styles()` 无条件加 `WS_CAPTION`，只有 `to_adjusted_window_styles()`
（仅用于算客户区）才在无 decorations 时移除。

### 19.3 改动

| 文件 | 改动 |
| --- | --- |
| `tauri.conf.json` | mini 加 `"shadow": false` —— 唯一直接消灭 DWM 那圈的手段 |
| `mini.rs` | `PANEL_PAD = 12`，窗口 320×300 → **344×324**（面板本体不变）；`toggle_mini` 显示后 `emit_to("mini", "mini-shown")` |
| `mini.js` | 抽出 `applyShapeSize()`，新增 `listen('mini-shown', realignShape)` —— 按当前形态重新对齐尺寸。不能复用 `setShape`，它有 `next === shape` 短路，而「形态没变」正是要修的场景 |
| `mini.css` `.orb` | 外发光 20px → **6px**（46+6=52 < 54）；新增 `::before`（球面明暗：34%/28% 受光、右下压到 34% 黑、底部一道 `--down` 环境反弹光）与 `::after`（受光方向小而锐的固定镜面高光）。两层都乘 `--island-op`，保持与桌面融合 |
| `mini.css` `.orb-halo` | 渐变末档从「100% 处仍留 10% 琥珀」改为**到 100% 归零**（原来元素边界本身就是一圈硬边）；`::after` 的向外 box-shadow 改 **inset** —— 光往球内走，最大半径就是 halo 自己的 51 |

设计上的两条新纪律，已写进 `mini.css` 文件头：

1. **透明窗口里所有发光必须收在窗口内。** 窗口边界是硬的，超出的光一律被裁成直线；
   圆形的光被方形窗口裁出来就是「四个角什么都没有 + 四条边中段各一条亮线」。
   球形态预算：一切光的最远半径 ≤ 54；面板形态预算：两层投影扩散之和 ≤ 12。
2. **球面光照是材质层，不随 `--e` 变。** halo/core/sheen 三层管「能量」，
   `::before`/`::after` 管「材质」——静默时能量层熄灭，材质层还在，球才不是一个死盘。

## 27. 阴影与发光收敛（2026-09-12）

## 29. 启动卡顿：采集端首帧三项修复（2026-09-12，用户反馈）

用户反馈：启动时经常有明显卡顿，启动好了就没事。

定位到根因是**首帧同步阻塞**：`SnapshotPipeServer` 里 `produceSnapshot()` 是同步
调用，`GetSnapshot()` 内部逐 PID 查进程元数据、逐路径提图标，全部做完才有第一个
字节进管道。耗时随开机时有网络活动的进程数线性增长；TTL 缓存（5s）一热，
每 PID 降到约 0.075ms —— 正好对应「启动好了就没事」。

### 三项改动

| # | 文件 | 内容 |
|---|---|---|
| 1 | `Sources/ProcessMetadataCache.cs` | `Process.GetProcessById` + `MainModule` 换成 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `QueryFullProcessImageNameW`，一个句柄同时取路径与启动时间 |
| 2 | `Sources/ProcessIconCache.cs` | 提取移出快照路径：后台单线程预取，帧内只取已就绪的（`TryGetDataUrl`） |
| 3 | `Sources/EtwSnapshotSource.cs` | ETW 会话改后台线程启动；`volatile bool _started` 换成 `SessionState` 三态（Starting/Running/Failed）；新增 `Status = "starting"` |

第 1 项的实测差距：老写法走 345 个路径 7350ms，新写法走 367 个路径 45ms —— 快约
160 倍，且解析出的路径更多。原因是受保护进程会拒绝 `MainModule` 需要的
`PROCESS_VM_READ`，却接受 LIMITED 查询。

第 3 项之所以必要：`collector.log` 里残留会话清理实测 0.3–2.4s，而 `StartSession()`
原先在构造函数里同步跑，这段时间挂在 DI 建 singleton 的路径上，`Host.Run()` 要等它，
管道也就跟着晚开。

### 顺带修掉的竞态

会话改后台建之后，`Dispose()` 可能先把 `_session` 读空走人，启动线程随后才
`new TraceEventSession` 并赋值 —— 那个会话就没人停了。ETW 会话是内核对象，
进程退出也不消失，会以「残留会话」留到下次启动，正好又变成要消除的那 0.3–2.4s。
两头都堵：`Dispose` 先 `Join` 启动线程（3s 上限），启动线程赋值前自查 `_disposed`，
是自己建的就自己拆。

### 前端配套

`starting` 是第四个 `Status` 值，而前端原先把「不是 ok 也不是 paused」一律当异常，
新状态会被渲染成「服务异常 · 需管理员权限」—— 每次正常启动的头几秒都撒一次谎。

| 文件 | 内容 |
|---|---|
| `ui/main.js` | `STATUS` 加 `starting` 项；新增 `statusKey()` 收敛映射，顶栏胶囊与设置屏服务字段共用；`PROC_STATES.starting` 用骨架条而非异常卡片 |
| `ui/mini.js` | `paintStatus` 拆出 `starting` 分支，状态点走黄不走红 |
| `Shared/Protocol/TrafficSnapshot.cs` | `Status` 文档注释补齐四个取值及各自含义 |

`pipe.rs` 的 `check_rate_alerts` 在非 `ok` 时早退，本来就是对的，未改。

### 验证（热启动实测）

| 阶段 | 改前 | 改后 |
|---|---|---|
| 管道开始接受连接 | 要等 ETW 会话建完 | 180ms |
| 首帧到达 UI | 8038ms（模拟测算） | 596ms |
| 状态转 ok | 同上 | 1597ms |

日志顺序的变化是关键证据：改前是「ETW 会话已启动 → 管道开始监听」，改后是
「管道监听(180ms) → UI 已连接(201ms) → ETW 会话已启动(1765ms)」。

`dotnet build` 零警告零错误；前端单测 6 文件全过；`node --check` main.js / mini.js 通过。

**测量陷阱记录**：第一次测出管道要 2836ms，那是冷启动假象 —— exe 刚编译出来不在
文件缓存里。同一个二进制第二次跑总计 417ms，其中 308ms 是 .NET 宿主启动 + JIT，
发生在第一行日志之前，与这三项无关。

**未动**：`CollectorService.cs:37` 每次 `ServeAsync` 前无条件调 `ResetIconStream()`，
UI 每次重连都重发全量约 143KB 图标。不影响启动卡顿，且改动涉及重连语义，另算一件事。
