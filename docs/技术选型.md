# NetPeek 技术选型

目标：Windows 常驻轻量工具，实时显示每个软件用了多少上传/下载流量。约束是低占用、免驱动、普通用户可用。

日期 2026-09-02。

## 0. 推荐组合

| 模块 | 推荐 | 备选（见下文） |
| --- | --- | --- |
| 采集数据源 | ETW `Microsoft-Windows-Kernel-Network` | WFP callout、EStats |
| 采集服务语言 | C# / .NET 8 | C++20、Rust |
| 桌面 UI | **Tauri 2**（2026-09-02 起，原因见 4.3） | WPF + WPF-UI（放弃动态背景时）、WinUI 3 |
| 主题引擎 | 自适应主题引擎：标准 + AI 双模式（见 4.3） | 固定深浅色主题 |
| 进程通信 | Named Pipe + 长度前缀 JSON | 共享内存、MessagePack |
| 本地存储 | SQLite（分钟聚合） | 二进制环形文件、LiteDB |
| 图表 | uPlot（canvas） | ECharts（按需引入） |
| 视觉规范 | 自定义设计系统（见 4.1） | 直接沿用主题库默认样式 |
| 安装发布 | WiX MSI（含服务注册） | Inno Setup、MSIX |

一句话理由：ETW 是唯一既能按进程归因、又不需要自带内核驱动的实时数据源；其余选择都围绕"少写代码、少占内存、能独立替换"。2026-09-02 起 UI 层目标新增“自定义背景 + 运行时自适应主题”，该能力以 Web 技术栈实现成本最低，故 UI 推荐由 WPF 调整为 Tauri 2（详见 4.3）。

## 1. 本机实测结论（不是推测）

2026-09-01 在本机启用 `Microsoft-Windows-Kernel-Network` 采集了一段真实流量，共 12698 条事件，分布如下：

| 事件 | 条数 | 用途 |
| --- | --- | --- |
| Data received | 4416 | TCP 下载计数 |
| Protocol copied data on behalf of user | 4250 | 应用层拷贝，**不计入**，否则重复 |
| Data sent | 3275 | TCP 上传计数 |
| Disconnect issued | 256 | 连接生命周期 |
| Connection attempted | 160 | 连接生命周期 |
| Data received over UDP | 97 | UDP 下载计数 |
| Data sent over UDP | 94 | UDP 上传计数 |
| Connection accepted | 71 | 连接生命周期 |
| Reconnect attempted | 66 | 连接生命周期 |
| Data retransmitted | 13 | 单独统计为重传 |

三条可以直接写进实现的事实：

1. TCP 与 UDP 的收发事件 payload 前两个字段就是 `PID` 和 `size`，后面是双向地址与端口。按进程统计不需要额外关联连接表。
2. **必须用 payload 里的 PID，不能用事件头的 PID。** 实测一条收包事件头部 PID 是 `14732`，payload PID 是 `33728`；发包事件两者才一致。只要用错，下载流量会被算到不相干的进程上。
3. `Protocol copied data on behalf of user`（Event ID 18）与 `Data received` 是同一批数据的两次观察，累加会导致下载量翻倍。

## 2. 采集数据源：6 个方案

这是唯一真正影响产品能力上限的选择，其余模块都可以后期替换。

### 2.1 ETW Kernel Network（推荐）

系统内置事件追踪，订阅内核网络事件即可拿到 PID、字节数、协议和地址。

- 覆盖 TCP、UDP、IPv4、IPv6，QUIC 走 UDP 也能统计到。
- 事件级实时，不需要轮询。
- 不需要自带驱动，不需要用户额外安装任何东西。
- 需要管理员或 LocalSystem 才能开启会话，所以要拆一个服务出来。
- 高包速率时 CPU 随事件数上升，缓冲区不足会丢事件，必须监控 `EventsLost`。
- 字节数是网络栈口径，不等于网卡线上字节，不含协议头。

### 2.2 WFP callout 驱动

在 Windows 过滤平台的 ALE 层拿应用身份，再在 STREAM / DATAGRAM 层计数。

- 精度和控制力最强，还能顺带做限速和拦截。
- 但要写内核驱动，需要 EV 证书签名、多架构、INF/CAT、升级卸载流程。
- 与杀软、VPN 共存需大量兼容测试，缺陷会直接蓝屏。
- 结论：首版不做。只有当 ETW 实测误差无法接受，或要做防火墙功能时才升级到它。

### 2.3 TCP EStats

`GetPerTcpConnectionEStats` 读取单条 TCP 连接的字节统计。

- 只有 TCP，没有 UDP/QUIC。
- 必须先发现连接再逐条启用统计，短连接和启用前的流量必然漏掉。
- API 本身不带 PID，要另外关联 `GetExtendedTcpTable`。
- 结论：不能当主链路，可作为长连接的对照校验。

### 2.4 WinRT Network Data Usage

`GetNetworkUsageAsync` / `GetAttributedNetworkUsageAsync` 读取系统已记账的用量。

- 最细只到每分钟，且官方说明是估算、会延迟，无法做秒级速率。
- 按应用的接口需要受限能力和商店审批，普通 Win32 程序不适合依赖。
- 结论：不采用。可作为"本月总量"的交叉参考。

### 2.5 pktmon

Windows 10 2004+ 内置的抓包与计数工具，零安装体积。

- 没有可靠的按进程归因，只能按五元组反查进程表，短连接会错。
- 同一个包会在多个栈组件被观察多次。
- 结论：不作为统计来源。适合做"抓最近 30 秒并导出 PCAPNG"的诊断功能。

### 2.6 Npcap

第三方抓包驱动，Wireshark 生态。

- 数据包本身没有 PID，归因靠猜，UDP 和入站流量尤其不准。
- 要装第三方驱动，商业分发还需 OEM 授权，安装包体积上 MB。
- 结论：不采用。

## 3. 采集服务语言：3 个方案

| 方案 | 优点 | 缺点 | 适合 |
| --- | --- | --- | --- |
| **C# / .NET 8**（推荐） | `TraceEvent` 库直接解析 ETW，开发最快；Windows Service 模板成熟 | 有 GC，工作集比原生高；需 AOT 才能压到较小体积 | 首版，快速验证 |
| C++20 | 内存和 CPU 最省，直接调 ETW/TDH；无运行时依赖 | 手写事件解析，开发和排错慢；容易出内存问题 | 性能预算不达标时替换 |
| Rust | 内存安全 + 原生性能，`ferrisetw` 可用 | Windows 服务与 ETW 生态不如前两者成熟，招人难 | 团队已有 Rust 经验 |

建议：先用 C# 把功能做对，把服务与 UI 的边界切干净。若服务内存超 40 MB 或高包速率 CPU 超标，只重写 `NetPeek.Collector` 为 C++，UI 完全不动。这是选型里最重要的一条风险对冲。

### UI 框架的具体取舍

**路线 A：WPF + WPF-UI（默认推荐）**

用 WPF 保持成熟的托盘、虚拟化表格和图表生态，再引入一个 Fluent 风格主题层。适合 NetPeek 的“轻量常驻 + 数据密集”定位；Mica、Acrylic、标题栏按钮和窗口圆角可以只在主窗口启用，不影响后台服务。要注意第三方主题库的维护活跃度和 .NET 兼容性，版本应在建立项目时锁定并做源码审查。

**路线 B：WinUI 3（视觉优先推荐）**

如果产品定位更像面向消费者的精致 Windows 11 应用，WinUI 3 的默认控件、暗色模式、Mica 和标题栏整合更自然。代价是 Windows App SDK 运行时/自包含部署、版本兼容、托盘和服务集成需要更多工程处理。它不会让采集服务更准确，主要收益是 UI 观感。

**路线 C：Tauri 2 + Web UI（设计自由度优先）**

可用 React/Svelte + CSS 做玻璃卡片、微动效和响应式布局，WebView2 复用系统运行时后比 Electron 轻很多。代价是 UI 线程、WebView2 安装状态、托盘、自动更新和高频图表数据通道需要额外测试；它仍通常比纯 WPF/WinUI 占更多内存。

**路线 D：Qt Quick / QML（性能与动效优先）**

适合要做非常定制化的仪表盘、流畅动画或未来跨 Windows/Linux 的产品。QML 比 Qt Widgets 更适合卡片、渐变和实时图表，但需要 C++/QML 团队和更严格的 Qt 授权评估；不适合第一版快速验证。

### 本轮结论

~~第一版仍建议 WPF + WPF-UI~~ **2026-09-02 更新**：新增“自定义背景 + 自适应主题”策略后，UI 推荐调整为 **Tauri 2**，理由与工程补项见 4.3 节。若放弃动态背景，回到 WPF + WPF-UI 仍是低成本选项。若用户验收标准是“必须原生 Windows 11 观感”，选 **WinUI 3**；若验收标准是“极致定制动效”，选 **Qt Quick**。

不要同时引入多个主题方案。Tauri 2 下定好一套设计令牌结构后，标准/AI 两种自适应模式只产出令牌，不再各自维护样式。

## 4.1 视觉规范（把“美观”变成可验收项）

界面结构：顶部是总上传/下载速率和状态；主区是进程列表；右侧或底部是所选进程的速率曲线；托盘图标显示实时速率。

- 排版：一套字号阶梯（如 12 / 14 / 20 / 28），流量数字用等宽或表格数字，避免刷新时列宽跳动。
- 间距：统一 4 px 栅格，卡片内边距 12–16 px，行高不低于 32 px。
- 颜色：上传与下载各一个固定色，深浅色主题各自定义；状态色只用于异常与限额提醒，不要整行染色。
- 主题：跟随系统深浅色，并允许手动覆盖；切换时不重启窗口。
- 动效：只做 120–200 ms 的淡入和数值过渡，列表滚动和排序不加弹跳动画。
- 图表：固定时间窗，只画 Top N 序列，隐藏窗口时停止重绘。
- 空态与异常：无数据、服务未启动、ETW 丢事件都要有明确文案，不要显示空白表格。
- 无障碍：正文对比度不低于 4.5:1，可键盘遍历，尊重系统“减少动画”设置。
- 高分屏：在 100%、150%、200% 缩放下检查图标、表格和图表不模糊、不错位。

界面美观性与性能预算同等对待：深浅色两套截图、三种缩放、窗口最小宽度下的布局都要通过检查。

## 4.3 三模式主题系统（2026-09-02 新增，2026-09-03 调整为三模式）

背景图用户自定义，UI 样式随图片自适应；同时支持不依赖背景的定制化主题。这是产品差异化功能，也直接改变了 UI 技术栈的结论。

三个并列模式共用一条流水线，输出同一组设计令牌：

```text
图片 / 手动设定 → 分析 / 直接映射 → 设计令牌（CSS 变量）→ 对比度校验 → 应用 → 可保存为主题
```

所有主题统一抽象为：名称 + 来源（standard / ai / custom）+ 设计令牌集 + 可选背景图路径 + 微调参数（面板不透明度、背景模糊强度）。主题列表支持保存、切换、重命名、删除，当前激活主题持久化。

**模式 1：自定义背景 + 标准离线取色（默认，离线，确定性）**

- 中位切分提取 8 色色板，统计亮度直方图与色温。
- 玻璃面板底色取最深主色；主/次强调色取饱和中间调并提亮到可读亮度；文字明暗按背景亮度自动选择。
- 全部令牌过 WCAG 4.5:1 对比度校验，不过则自动调整明度直到通过。
- 焦点避让用显著性检测（频谱残差即可，无需重型模型），面板默认放到画面最不显著的一侧。
- 完全离线、即时生效；提供面板不透明度、背景模糊强度两个微调滑杆。

**模式 2：自定义背景 + AI 自适应（可选增强，结果可保存为主题）**

- 把缩略图和令牌 JSON schema 发给多模态模型，返回配色、明暗倾向、焦点区域。
- 输出必须过同一个对比度校验器，不过则回退标准模式；标准模式同时是默认项和 AI 的兜底。
- 结果按图片内容哈希缓存，同一图不重复请求；**生成的主题可命名保存到主题列表**，后续直接切换复用，无需重新调用 AI。
- 隐私：用户壁纸缩略图会离开设备，首次使用需明确授权，提供方可选，并保留”仅标准模式”选项。

**模式 3：定制化主题（不依赖背景图）**

- 内置预设主题若干（如经典深色、经典浅色、高对比等），一键启用。
- 用户可手动定制各设计令牌（主强调色、次强调色、面板底色、文字明暗等）及微调参数，保存为自定义主题加入主题列表。
- 同样过 WCAG 4.5:1 对比度校验，不通过时给出提示并自动修正明度。

**对技术栈的影响**

UI 只订阅令牌，不感知令牌来源（三种模式 / AI 提供方云端 API、将来的本地小模型，均可插拔）。自定义背景层 + `backdrop-filter` 玻璃 + 运行时 CSS 变量换肤是 Web 的原生能力；WPF/WinUI 做同等动态主题要多一层资源字典与合成器手工活。因此 UI 推荐由 WPF + WPF-UI 调整为 **Tauri 2**（采集服务 C#/.NET 8 不变，二者本就通过 Named Pipe 解耦，替换 UI 不影响采集）。若后续决定放弃动态背景，回到 WPF + WPF-UI 仍然是低成本选项。

**Tauri 2 路线需要补的工程项**

- WebView2 运行时检测与引导安装（Win10 1803+ 大多已有，仍要兜底）。
- 高频刷新的性能纪律：速率与表格更新走局部状态，禁止整树重渲染；图表用 canvas 库（uPlot / ECharts 按需）而非 SVG 高频改 DOM。
- 托盘用 Tauri 原生 tray API；开机自启、单实例、窗口记忆位置用官方插件。
- 服务通信沿用 Named Pipe（Rust 侧 `tokio`/`interprocess` 均有成熟实现），IPC 协议不变。

## 5. 进程通信：3 个方案

| 方案 | 说明 | 取舍 |
| --- | --- | --- |
| **Named Pipe + 长度前缀 JSON**（推荐） | 每秒推一次聚合快照，几百个进程也就几十 KB | 实现简单、可读、便于排错；必须设 ACL 限制访问者 |
| 共享内存 + 环形缓冲 | 零拷贝，延迟最低 | 只有在每秒推送上千行时才值得，现在是过度设计 |
| gRPC / localhost TCP | 工具链完善 | 开本地端口会被防火墙和杀软盯上，不适合 |

两条硬规则：绝不把每条 ETW 事件跨进程传输；服务只暴露带 ACL 的管道，不监听网络端口。

## 6. 本地存储：3 个方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **SQLite**（推荐） | 聚合查询、保留策略、导出都方便；单文件 | 需注意批量事务，避免每秒写盘 |
| 自定义二进制环形文件 | 体积最小，写入最快 | 查询和聚合全要手写，改格式就得迁移 |
| LiteDB / JSON / CSV | 上手快 | 时间序列聚合性能差，长期数据会膨胀 |

只存分钟级聚合，不存单条事件。默认保留 30 天分钟数据，更早的压成小时或日汇总。

## 7. 安装发布：3 个方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **WiX MSI**（推荐） | 能规范注册/启动/卸载 Windows Service，支持企业分发和升级 | 学习曲线陡 |
| Inno Setup | 脚本简单，出包快 | 服务与升级逻辑要自己写，企业部署支持弱 |
| MSIX | 安装干净、自带更新 | 打包应用装传统服务受限，与本架构不匹配 |

发布需签名，否则 SmartScreen 会拦。

## 8. 整体路线对比

| 路线 | 组合 | 观感 | 何时选 |
| --- | --- | --- | --- |
| **A 快速可用**（推荐） | ETW + C#/.NET 8 + **Tauri 2** + SQLite | 品牌化 + 自适应主题 | 首版默认。采集与 UI 经 Named Pipe 解耦 |
| B 视觉优先 | ETW + C#/.NET 8 + WinUI 3 | 最贴近 Win11 | 验收标准是“必须原生 Win11 观感”，且放弃自定义背景 |
| C 保守均衡 | ETW + C#/.NET 8 + WPF-UI | 现代 Fluent | 放弃动态背景、只保留固定深浅色主题时 |
| D 极致轻量 | ETW + C++20 + Qt Quick/Win32 | 定制动效强，成本高 | 要求服务 <15 MB、安装包 <5 MB |

## 9. 统计边界（必须写进产品说明）

NetPeek 显示的是 Windows 网络栈观察到、并归因到进程的字节数，不等于网卡实际收发量。差异来自协议头、TCP 重传、网卡卸载、回环通信。

必须向用户明说的归因限制：

- 走本地代理时，外部流量归到代理进程。
- 走 VPN 时，隧道流量归到 VPN 服务。
- WSL / Hyper-V / 容器流量归到 `vmmem` 或 Host Network Service。
- `svchost.exe` 内多个服务共享进程，无法天然拆分到单个服务。
- 浏览器多个子进程应在界面上聚合，同时保留进程级明细。

不要把接口总量与归因总量的差额按比例摊给各应用，只能单独显示为"系统 / 未归因"。

## 10. 已确定的实现细节

进程身份键用 `PID + 进程启动时间`。只用 PID 的话，进程退出后 PID 被复用，历史流量会算到新进程头上。

ETW 回调里只做三件事：读 payload PID、判方向、累加计数器。查图标、验签名、写数据库、推 UI 一律放到回调之外，否则高流量时会放大 CPU 占用和事件丢失。

事件处理规则：`Data sent` / `Data received` / UDP 收发计入主统计；Event ID 18 忽略；`Data retransmitted` 单独统计为重传，不混入应用上传量。
