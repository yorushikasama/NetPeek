### 1.2 语义部件（动效"演员"）

| id | 部件 | 几何摘要 |
|---|---|---|
| `#pulse-glow` | 主波辉光 | 主波路径的加宽模糊复制（stroke 30 + σ=11），伴生、滞后主波 140ms |
| `#pulse-line` | 琥珀主波（**主角**） | 左平段 y=632.5 → 峰 (628, 457) → 谷 (716, 691) → 右平段；**5 段直线 + 4 个圆角** |

**与初版 brief 的重要更正**：初测把"每 4px 采样步长稳定"读成"是折线、转折为单点尖峰"。
按 50% 覆盖率口径重测后确认**四处转折都是圆角**，峰/谷的墨迹极值不能直接当中心线顶点
（round join 会让墨迹比中心线多出半个描边宽）。这一条直接决定了拟合方式 ——
见 Phase 2。若沿用"尖峰折线"的做法，四个转角处会稳定差 8–12px。

### 1.3 Motion Brief

**Personality（3 个品牌动效词）：迅捷、精密、有生命感。**
- *迅捷* ← 折线的长平段 + 极陡的斜段，速度反差本身就是"突发流量"的视觉隐喻；
- *精密* ← 平段严格水平、两段斜率绝对值几乎相等（2.54 / 2.55），是工程制图而非手绘质感；
- *有生命感* ← 波形即脉搏，这也是 NetPeek 的产品本体（在实时测一个活着的系统）。

与 `DESIGN.md` 对齐：设计系统要求动效只表达"采集、选择、切换、反馈"状态且强调克制。
启动动效对应的是**采集服务启动 + 首绘**这一段状态，因此被许可；
姿态必须是"揭示"而非"表演"——不喧哗、不抢数据。

**Usage context：应用启动揭示（boot reveal）。**
- 时长带 1200–2000ms（skill 规定）。最初取 1400ms，**后因观感过快调整为
  2000ms 动效 + 400ms 定格 = 2400ms**（诊断与依据见 §3.6）；
- 它覆盖的窗口期是真实存在的：采集端首帧约 596ms（见 `docs/开发进度.md` §29），
  界面侧还要等主题、设置、历史库三次 IPC。把这段"什么都还没有"的时间
  交给品牌动效，而不是让用户盯着一个空表格。
- 终态：QA 验证过的静态矢量（Final Frame Contract），随后整层卸下交给真实界面。

### 2.2 拟合口径

**为什么不能拿墨迹边缘当中心线**：源图有底片、渲染是透明的，固定亮度阈值必然不公平。
统一改用**逐列 50% 覆盖率** —— 抗锯齿边缘上"信号穿过 (峰值 − 10 分位底色) 一半"的位置
就是几何描边边缘，这个判据与背景色无关，深浅底都成立。

**线段**：最小二乘 + MAD 稳健剔除（剔除 |残差| > max(0.6, 3·MAD) 且封顶 2.5px 的点）。
最终 5 段残差 RMS **0.06–0.26px**。

**圆角**：以二次 Bézier `P0=C+t·u₁, P1=C, P2=C+t·u₂`（C = 两直线交点）建模，
切点长度 `t` 通过"最小化**只对已离开两条直线的点**（偏离 >0.9px）的最大偏差"反解。
两个坑都踩过：
- 用"沿角平分线的最大投影"求 t → 直线上的点投影也线性增长，最优解跑到窗口边界（解出 140 这种废值）；
- 用"全部点的最大偏差"求 t → 直线点把偏差压到 0，t 被拉向 0，转角变成硬折。

峰顶/谷底是 `y(x)` 的多值区，逐行/逐列都不好用，改用**墨迹包络约束**：
峰顶墨迹上缘 y=446 + round join 半径 = 中心线极值 y=457。

最终误差（`overlay_qa.py`）：

| 部件 | 覆盖率 | 线宽差 | 中心线 Δcy RMS / max |
|---|---|---|---|
| 主波 | 0.995 | −0.08px | 1.067 / 3.5px |
| 次波 | 0.979 | −0.26px | 0.642 / 2.0px |

扣掉约 1px 的常量偏移后，形状误差 ≈ **0.36px**。

### 2.3 字标

从 `seguisb.ttf`（Segoe UI Semibold 5.71）经 fontTools `SVGPathPen` 取描边。

- 不写 `<text>`：动效资产必须**确定性**，`<text>` 的最终宽度取决于渲染机装了什么字体；
  且逐字形元素才能做揭示动效。
- **按墨迹对齐，不按基线/CapHeight**：CapHeight=1434，但 `k` 的上升部到 1516（+5.7%）、
  `e` 的弧底到 −24（−1.7%）。拿 CapHeight 当顶边，整行字标会往下掉约 6% 字高。
- 归一化基准 CapHeight=100；“NetPeek” 总前进宽度 7778 units = 542.4。

### 2.4 锁定版式（lockup）

版式**全部由脚本从路径 `d` 真算**，不手填 translate/scale —— 波形一旦重拟合，
手算的 scale 会以"看着还行但差几像素"的方式失效，那是最难发现的一类。

画布 1180×720（= 主窗口设计尺寸，`tauri.conf.json`）：

| 量 | 值 |
|---|---|
| 波形墨迹 | 400.0 × 198.0（宽高比 2.020），源盒 `[225.25, 445.219, 1024.75, 840.933]` ×0.500313 |
| 字标墨迹 | 360.0 × 72.9（CapHeight 67.87），×0.04733105 |
| 间距 | 56.0（波形底 → 字标顶） |
| 整块 | y 196.6 → 523.4，高 326.9；**上下边距都是 196.6**（真居中）、左右 390 |
| 字标/波形宽比 | 0.9000 |

**尺度为什么从 560 收到 400**：560 时波形占窗口宽 47%，整块的横向跨度到 97%
（左右各只剩 19px），读起来像"把整行铺满"而不是"居中放着一个标记"。
400 → 34% 宽，左右各留 182px，四周才有呼吸。
`MARK_W` / `WORD_RATIO`（0.90）/ `GAP_RATIO`（0.14）三个常量在 `compose_lockup.py` 顶部，
**改大小只动 `MARK_W`，其余按比例派生** —— 间距必须跟着标记一起缩，
否则标记变小、间距不变，两者会读成"离得很远的两个东西"而不是一个 lockup。

**居中为什么改成算的**：原来是硬编码 `MARK_TOP = 117`，整块 117→574.2 落在 720 里是
"上 117、下 145.8"，比真居中高了 14.4px。偏差本身看不出来，但真正的问题是
"居中"这件事在代码里**根本没有表达** —— 尺度一动就必然更偏，而偏了没有任何东西会报错。
现在从画布高度反推 `mark_top = (VIEW_H - block_h) / 2`。

**外发光不参与版式计算**：拿发光算包围盒会让标记整体缩小并偏上（发光两侧各外扩约 20px）。

## Phase 3 — MOTION

### 3.1 时间线（2000ms 动效 + 400ms 定格）

| 时刻 | 元素 | 变化 | 时长 | 缓动 |
|---|---|---|---|---|
| 0 | `#np-lockup` | 上浮 10px→0 + 淡入 0→1 + 缩放 98.5%→100% | 520ms | `cubic-bezier(.05,.7,.1,1)` M3 emphasized-decelerate |
| 300 | `#pulse-line` | 描线 `dashoffset 1→0` | 960ms | `cubic-bezier(.42,0,.58,1)` 经典 ease-in-out |
| 440 | `#pulse-glow` | 同上（滞后主波 140ms） | 960ms | 同上 |
| 720 | `#pulse-echo` | 同上（滞后主波 420ms） | 840ms | 同上 |
| 1020 | `.np-glow-wrap` | 呼吸 `.55→.86→.55`，峰值落在 45% | 680ms | 同上 |
| 1380 | `#np-word-clip-rect` | 擦除推移 | 620ms | 同上 |
| 2000 | — | **定格**（什么都不动） | 400ms | — |
| 2400 | `.np-boot.is-out` | 内容先缩到 97.2% 淡出、幕布晚 100ms 揭开 | 220 / 360ms | `cubic-bezier(.3,0,.8,.15)` M3 emphasized-accelerate |

**扫速是这条时间线上唯一要盯的派生量**（标记宽 / 时长，单位 px/ms）：

| 元素 | 旧 | 新 |
|---|---|---|
| 主波 | 560 / 620 = **0.90** | 400 / 960 = **0.42** |
| 次波 | 540 / 560 = 0.96 | 386 / 840 = 0.46 |
| 字标 | 504 / 400 = **1.26** | 360 / 620 = **0.58** |

改 `MARK_W` 时必须重算这三行 —— 时长不是独立的自由度，它是和尺度绑在一起的观感量。

- **描线**：三条路径都带 `pathLength="1"`，进度统一成 `dasharray:1; dashoffset 1→0`。
  不依赖运行时 `getTotalLength()` —— 那条路会在动效起来之前闪一帧全亮的线。
- **擦除揭示**：让裁剪矩形自己左移一段，而不是动它的 `width`。
  动 SVG 几何属性各引擎支持度不一；动 `transform` 处处都稳，且在合成器上、不触发布局。
- **发光拆两个元素**：外层 `<g>` 管不透明度、内层 `<path>` 管描线，
  保证"一条元素一条动画"——截帧按 `currentTime` 定位时不用按动画分别算。
- **缓动取自 Material 3 的 motion token**，不自己编曲线：描线的起手快慢差 0.05，
  观感就从"有笔锋"滑到"弹出去"，手调没有判据只能来回试。
  `decel` 用于进场（开始快、结束慢）、`inout` 用于描线（起手慢、中段匀、收笔慢，
  最接近真实书写）、`accel` 用于退场（越走越快才不黏）。

### 3.2 两条硬约束

1. **最终帧 == 基础样式。** 所有 `@keyframes` 只描述过程，动画结束或被禁用时元素落在终帧。
   所以 `#pulse-line` 的基础值是 `dashoffset: 0`（画完），`0%` 才是 `1`。
   反过来的写法（基础=隐藏、动画去揭示）会让任何一次动画失败都变成一片空白。
2. **底色不参与动画。** 曾经给整层挂过 opacity 0→1 的淡入，去掉了 ——
   淡入的 0% 是全透明，而全透明意味着底下的界面会透出来，
   而启动层存在的全部意义就是"在界面没就绪时挡住没就绪的样子"。

### 3.3 截帧与定位

`?t=` 与拖动时间轴都走 Web Animations 的 `currentTime`，CSS 里只有一套时间线。
曾经用过"把 t 写进 `animation-delay` 的 calc 里"的写法，看着优雅，实际是错的：
**暂停一个已经在跑的动画，它的停表时间是"暂停那一刻已经走了多久"**，
这个值取决于页面加载时序 —— 于是 t=100ms 的帧里混进了几十毫秒、且每次冷启动都不同的偏移。
表现是"主波在 t=100ms 已经画了一半"，而设计是 150ms 才起笔。
数字对不上的 bug 最难查，因为它每次复现结果都不一样。

### 3.4 配色

| 位置 | 值 | 理由 |
|---|---|---|
| 主波（深底，默认） | `#f49d49` → `#fbd77f` → `#f0a14a` | 源图本色。对深底 7.9 / 12.2 / 8.0 : 1 |
| 外发光（深底） | `#f08a2a` + `feGaussianBlur σ=11` | |
| 次波（深底） | `color-mix(--text 32%)` → 实测 **2.02:1** | 见下 |
| 字标 | `--text` | 跟皮肤 |
| 主波（**浅底**） | `#a35a08` → `#c8751a` → `#9d560a` | 见下 |
| 次波（**浅底**） | `#a8aeb7` → 实测 **2.01:1** | |
| `preset-chrome` | 中性反白（`#c9cdd4`/`#f4f5f7`/`#d7dade`） | 完全合规的可选预设 |

**为什么默认允许出琥珀色**：`tokens.css` 写着"chrome（导航选中、表格选中、主按钮、品牌标）
全部走中性反白；琥珀只属于下载数据语义"。启动页是全应用唯一一个品牌可以带色的位置 ——
那条约束管的是界面内的控件与选中态，而品牌露出就是这一刻。
应用内的顶栏品牌标仍是中性单色（`currentColor`），两者是同一套品牌系统的两个用法。
要完全合规，把 `preset-chrome` 挂到 `#bootLayer` 上即可（`NetPeekBoot.setPreset('chrome')`）。

**次波为什么不是源图那个 `#2A2F2F`**：源图是深色线压在深色底片上，搬到深色皮肤会直接消失。
它的语义是"主波的伴生回波"——比底色亮一档、比主波弱得多，所以按 `--text` 派生。

**浅底必须换一套（`is-light-bg`，由 `boot.js` 按 `--bg` 实际亮度挂上）**：

- 深底的峰顶 `#fbd77f` 对浅底 `#f2f3f5` 只有 **1.25:1** —— 不是"弱一点"，是那条峰整个化掉，
  形状读起来变成断线。浅底换同色相、压过明度的一套，最低 3.14:1（卡在 WCAG 非文本 3:1 之上）。
- 次波用百分比派生跨底色**不成立**：到 2:1 深底需要 16%、浅底需要 72%，
  相差四倍多（sRGB 混色不保感知线性）。所以浅底直接给实测值。
- 为什么不按"皮肤 id 是 light"判断：皮肤分深/浅/跟随背景图三类，
  跟随背景图皮肤下真正决定观感的是用户选的壁纸，深浅未知。**直接量底色的亮度**对三类都成立。

**D 的判据为什么允许"边缘抗锯齿差"**：带 `fill` 的动画会把元素提升成独立合成层，
Chromium 对软边（模糊的发光）会换一套采样网格，于是每个形状边缘会差 1–2 级，
全幅约 1% 的像素。肉眼不可见，但它会让"逐像素相等"这种断言永远红着 ——
而一条永远红着的断言等于没有断言。所以判据改成"**差异必须只剩 1px 宽的轮廓**"：
对差异掩膜做形态学腐蚀，实心区域会被保留、轮廓会被抹掉；实测腐蚀后只剩 3px（噪声量级），
而真正的形状变化（少画一截、位移 1px、元素没画出来）会产生成百上千个。两者差三个数量级。

### 3.6 为什么从 1400ms 改成 2400ms（「死快死快的」诊断）

初版总长 1400ms，用户反馈"死快死快的"。逐个量完之后是四个原因叠加，
不是"把时长乘二"能解决的 —— 四条里只有第一条是时长问题：

1. **扫速过高。** 主波 560px / 620ms = **0.90 px/ms**，字标 504px / 400ms = **1.26 px/ms**。
   眼睛跟不上笔画前沿，"被画出来"的过程感就没了，只剩"唰一下"。
   → 降到 0.42 / 0.58 px/ms（见 §3.1 的扫速表）。
2. **缓动选错方向。** 原来三条线都用 `cubic-bezier(.25,.7,.35,1)`，这是条**减速**曲线：
   前 30% 的时长走完约 50% 的路程，**起手那一下是弹出去的**。
   这才是"快"的主要来源 —— 总时长看着不短，但最该被看清的起笔一闪而过，
   后面大半时间反而是慢的。→ 换成 ease-in-out，慢起、匀走、慢收。
3. **零定格留白。** 字标 1330ms 擦完、1400ms 就开始卸幕，中间只有 70ms。
   人眼要 200~400ms 才能把"刚刚成形的东西"登记下来。
   没有这段留白，用户看到的就是"一闪而过，没看清长什么样"。
   → 末帧后加 **400ms 定格**，它才是这个动效唯一的落点。
4. **相位差太挤。** 三条线挤在 240ms 内先后起跑，视觉上并成一个爆发，
   读不出"主波 → 发光跟着 → 回波补上"的次序。→ 拉开到 140ms / 420ms。

顺带改掉的：退场从"260ms 把内容和幕布一起淡掉"改成两段式
（内容先缩到 97.2% 淡出 220ms，幕布晚 100ms 起、360ms 揭开）。
一起淡掉读起来是"整块画面被擦掉"，分开之后交接有主次，像收场而不是切断。
退场用加速曲线 —— 离场要越走越快，用进场那条减速曲线会显得黏。

**外部的参照**（不是自己拍脑袋定的数）：
- Android 官方的 splash 规范：图标动效 **≤1000ms**、延迟启动 **≤166ms**（那是手机，
  启动页在挡操作）；而通用 logo 动效指南给的 "splash screen = 2–3s 品牌时刻"，
  桌面端窗口已经算出来之后更接近后者。2400ms 落在后者区间内。
- 「动效短于 0.5s 会显得仓促」「永远不要用 linear」是通行的两条 motion 原则，
  初版违反的是"仓促"这条的对称面 —— 单段不短，但**有效可读时间**很短。
- 描线的缓动，主流做法（CSS 教程、anime.js / GSAP 的 path drawing 示例）
  一致用 ease-in-out / sine 类，而不是 ease-out。
