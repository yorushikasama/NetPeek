## 核查用户提问：「排序键只看下载…上传重的应用掉出榜外」有这个问题吗（14:55）

**溯源**：这句话出自仓库里的注释，不是外部评审 —— `src/NetPeek.App/ui/history-ui.js:296-298`
与 `src/NetPeek.App/ui/index.html:313-317`，讲的是**历史屏「应用排行」卡**把排序键从「按下载」
改成「按合计」的理由（卡头标签现在是「按合计」）。所以「掉出榜外」指的是那张**有 TOP_N 截断的榜**。

**逐处核过的五处口径（结论：一半真）**：
| 位置 | 排序键 | 证据 |
|---|---|---|
| 实时屏 · 表格默认顺序 | **只看下载** | `main.js:447 DEFAULT_SORT = {key:'download',dir:-1}`；取值器 `main.js:435 download: p.DownloadBytes` |
| 实时屏 · 整行占比条 `--share` | **只看下载**，且按 `peakDown` 归一 | `main.js:677`、`styles.css:619-623`（`--down` 色渐变） |
| 迷你窗 Top 5 | 合计 | `mini.js:196-197` `(b.DownBytes+b.UpBytes)` |
| 历史屏 应用排行 | 合计 + `slice(0,TOP_N)` | `history-ui.js:316-317` |
| 采集端 快照顺序 | 合计（**累计**） | `EtwSnapshotSource.cs:487-489` `DownloadTotal+UploadTotal` |

**「掉出榜外」在实时屏不成立**：`renderTable`（`main.js:684-702`）遍历 `visibleProcesses` 全量渲染，
无 slice / TOP_N；`visibleProcesses`（`main.js:469-472`）唯一过滤是搜索框，**没有「只显示有流量」的开关**
（`main.js:745` 的 `idle` 是空态文案，不是过滤器）。上传重的行一定还在，只是可能沉到滚动视口之下
（表格是滚动容器，滚动边缘状态见 `main.js:1040-1049`）。
细节：并列 `DownloadBytes===0` 的行靠稳定排序退回采集端顺序，而那正是累计合计降序 —— 并列那一批
内部反而合理。

**真问题（比排序更硬）**：占比条只看下载 + 按下载峰值归一 ⟹ 上传重的行背景条≈0 宽，
**即便用户点「上传」列头把它排到第一，条还是空的**。

**待用户拍板**：① 只改占比条为合计口径（与历史屏 `history-ui.js:319` 同源）② 默认排序加 `total` 键
③ 两个都改 ④ 只把那条歧义注释改写（它把「实时屏」写成反例，读起来像实时屏也有截断）。

**用户选择：③ 两个都改**（已落地，见下）

## §49 落地：默认排序键与占比条统一到合计口径

**改动**（`ui/main.js` / `ui/styles.css` / `ui/history-ui.js` / `ui/index.html` + 单测 + 预览）：
1. `DEFAULT_SORT.key: 'download' → 'total'`，`sortAccessors` 新增 `total = down+up`。
   合计**没有对应列头** ⇒ 点任何一列的第一下都会真的重排（此前点「下载」第一下行序不动）。
   取消排序（第三次点 / 卡片头按钮）回到的就是它。
2. 占比条抽成纯函数 `shareOf(p, peak) → {pct, dir}`：分子 = 合计；分母 = `renderTable` 的
   `peakTotal`（合计峰值，与默认序同源 —— 满格那一行就是第一行）；`dir = down>=up ? 'down':'up'`，
   JS 写 `--share-color: var(--down|--up)`，CSS 走
   `color-mix(in srgb, var(--share-color, var(--down)) 9%, transparent)`；**只在方向翻了才写变量**
   （1 Hz 下每帧重设自定义属性会打断背景过渡）。历史屏 `rank-row::after` 一并对齐。
   用自定义属性而不是两个类名：行上已有 `is-selected` 在切类、且那层 9% 淡色要继续跟主题走。
3. 顺手把两处歧义注释改准（`history-ui.js` / `index.html`）：那里「实时屏」是**对照物**，
   「掉出榜外」只属于**有 `TOP_N` 截断的历史屏**；实时屏全量建行、一行都不少，只是可能沉到视口外。

**验收**：单测 12/12（table.test 85 项：新增 `shareOf` 一节（纯上传满格 / 方向 / 五五开取下载侧 /
峰值为 0 不出 NaN / 封顶）+ 「未排序 = 合计降序」**回归锁**（样本刻意让两种口径给出不同顺序）
+ `renderTable` 分母断言）；浏览器回归 1688 行 **0 FAIL**，新增 `[tag] share-bar`：
① 口径 —— 预览里 OneDrive（上 4.4e4 / 下 6.2e3）的 `--share ≥ 1`（按下载口径是 0%）；
② 接线 —— 把它的 `--share-color` 临时改红，`background-image` 必须跟着变
（「变量写了但 CSS 没接线」是这类改动最容易的静默失败）。另留 `[tag]-share-bar.png` 特写。

**踩到的坑（本轮最值钱的一条）**：改完先跑回归，`sort-cycle` / `sort-reset` 四条 FAIL
（判据是 `off.order === baseOrder`）。查下来**不是实现回归** —— 是**预览假桥的抖动带行号相位**
（`sin(tick/4 + i)`），「哪一行更大」随 tick 漂移。下载口径下 12 行只有 1 处相邻比 ≤1.5，
换成合计后变成 **4 处**（msedgewv2 1.23 / steam 1.30 / OneDrive 1.47 / Spotify 1.20）⇒
行序在几百毫秒内自己换位，而 `baseOrder` 是几秒前抓的快照。抖动改成**同相**（不带 `i`）后
相对顺序恒定，条读数也从 4% 稳定到 2%。
**教训：换排序键会连带改变「哪些行相邻」——基于行序的断言要先检查数据基准稳不稳**
（`baseOrder` 这类快照断言天然假设「顺序在抓取间隔内不变」）。

## 历史屏自定义区间：按主流产品的做法重做交互（16:50，同日前半天接着做）

用户连贴两张图否定同一处：① 「这个设计不好，你上网看看别人是怎么设计这里的交互的」
（`开始[日期][00:00 置灰] ~ 结束[日期][23:59 置灰] 超过3天，按天聚合 [应用][取消]`）；
② 「时间选择器的样式和目前的主题不适配」（原生 `input[type=time]` 的弹层：灰石板底 + 亮蓝选中格）。

**上网核到的口径（这次改动的依据）**：
- Grafana：绝对区间就是 `From`/`To` 两个字段摆在展开面板里，**粒度从来不是用户输入**
  （Min interval / Max data points 藏在面板配置里），区间变长只是柱子变粗。
- Visa 设计系统：日期+时刻并排时中间用 `to` 串起来；**「All day」是勾出来的**，
  不是「长到某个阈值自己灰掉」。空间紧张就垂直堆叠 + 每行左侧带标签。
- Salesforce 系 / uxpatterns.dev / 21st.dev：预设档是硬要求；反模式之一是「改开始日期顺手清掉结束日期」。
- 结论：**原来的错不在「置灰」这个决定，而在把实现细节当成了表单状态。**
  `HOUR_MODE_MAX_HOURS=72` 是**渲染**约束（720 根小时柱画不下），界面却表达成「控件不可用」。

**落地（`ui/index.html` / `styles.css` / `history-ui.js`）**：
1. **粒度从「表单状态」降级成「回执」**：底部一行 `按小时聚合 · 共 18 小时` /
   `按天聚合 · 共 11 天（超过 3 天，时刻不参与）`。回执读 `planQuery` + `hourKeysBetween`/`spanDays`
   的**同一套骨架**，所以「共 N 小时」和点完之后真有的根数永远一致。按天档还分天/周两级
   （`WEEK_AGG_THRESHOLD`），回执跟着走 —— 长到按周了还说「按天」是错的。
2. **版式改成两行**：第 1 行字段，第 2 行「回执（左）+ 按钮（右）」（`.hist-range-foot{flex:1 1 100%}`），
   按钮位置在两种粒度间不跳。
3. **不置灰，收起**：超 72h 整块 `.hist-time-wrap` 收起。灰控件读作「坏了/没权限」，
   而事实是「这一档用不上时刻」—— 那是回执该说的话。**收起不清空**，改回去时上次选的整点还在。
4. **默认值从「整个可见区间」改成今天**：原来一打开就是近 30 天 → 按定义走整日聚合，
   用户第一眼看到的就是一组用不上的控件。落今天则天然是小时档。
5. **时刻控件换成 `select[data-menu]`**（复用 select-menu.js 的呈现层）：25 个取值
   （全天 + 24 整点）本来就是离散量，语义正着；顺带把 Chromium 的 PagePopup 整个消掉
   （`input[type=time]` 右端钟表按钮弹的是独立文档，页面 CSS 够不着，与日期框同一个根因）。
   `.sel-btn` 的 170px 下限按这一处收窄。
6. 表单级监听**必须同时听 `input` 和 `change`**：select-menu 选完只冒 `change`
   （写的是 `select.value`，程序化赋值连 `input` 都不冒）。

**踩到的三个坑（这轮最值钱的部分）**：
- **Esc 跨层**：`select-menu.js` 的 Esc 分支只 `preventDefault()`、没有 `stopPropagation()`，
  而 `date-picker.js` 早就有。于是按 Esc 同时收下拉**和它所在的自定义表单**
  （history-ui 在 document 上监听 Esc 收浮层）。回归里的症状是下一步点时刻框超时、
  报「元素不可见」——离真相很远。修：select-menu 也 `stopPropagation()`；
  preview-v2 加锁「Esc 只收一层：表单还开着 + 下拉已收」。
- **新增的 `.sel` 抢了旧探针的首次匹配**：preview-v2 设置屏那段用 `.sel .sel-btn` /
  `document.querySelector('.sel-pop')`，而历史屏的自定义表单在 DOM 里排在设置屏前面，
  于是命中了关着的表单里那两个 → 超时「元素不可见」。改成按
  `.screen[data-screen="settings"] .sel` 圈定。
- **「共几小时」会随钟点翻的断言**：`planQuery` 把上界夹到「现在」，所以「今天 00:00~18:00」
  的格数取决于跑测试的时刻。断言改用**昨天**（两端都在过去）→ 死的 18 格。

**验收**：单测 12/12（含 dom-contract）；`cargo test --release history` 23/23；
浏览器回归 **47 项 0 FAIL**，新增 6 条 hist-custom 断言 × 2 视口，另有
`-history-time-menu.png` / `-history-custom-wide.png` / `-history-custom-hour.png` 特写。
