## 托盘状态同步排查（2026-09-14 下午，只查未改）

用户报「系统托盘那里的状态好像没有跟实际状态同步」。做了**真机实测**（不是只读代码）：
托盘菜单是 explorer 的原生 HMENU，Web 侧/headless 都看不到，为此写了外部观察者工具
`C:\Users\Administrator\.workbuddy\tmp\trayprobe`（.NET 8 控制台，`dotnet build -c Release`）：
- `trayrect` 定位任务栏。**本机任务栏是自动隐藏的**（`Shell_TrayWnd` rect 平时顶在 y=1198≈屏高，
  鼠标移到屏幕底部才滑出到 y=1128）；`TrayNotifyWnd` 在 x=1509..1920。屏幕 1920×1200。
- **必须先 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`**，否则 `GetWindowRect` 与
  `CopyFromScreen` 活在两套坐标系里，截出来的"任务栏"是 IDE 状态栏（实测踩坑）。
- `shot x y w h` 区域截图；`move`/`lclick`/`rclick`/`esc` 模拟操作。
- **NetPeek 托盘图标默认折叠在溢出区**（`^` 箭头，x≈1515,y≈1164），展开后图标在约 (1426,1010)。
- UIA 读不到 Win11 托盘的 XAML 图标（`Shell_TrayWnd` 整棵子树只有 2 个 UIA 元素），
  所以只能靠截图判读 —— 但这条路验证原生菜单文本是可行的。

**实测结论（决定性）**：通过控制管道发 `pause` 后，托盘右键菜单文案**确实**由「暂停监控」变成
「恢复监控」——`muda::MenuItem::set_text` → `SetMenuItemInfoW(托盘自己的 hpopupmenu)` 链路**正常**，
§13.1 的修复有效。**同一时刻 tooltip 恒为 `NetPeek`**（截图里能看到悬停气泡）。

代码审查确认的缺陷（均未修）：
1. 托盘对「离线 / ETW error / starting」三种状态**零表达** —— tooltip 恒 `NetPeek`、图标恒
   `icon-32.png`、菜单只区分暂停/未暂停。主窗关到托盘后托盘是唯一状态出口，它不说话。
2. 服务离线时点托盘「暂停监控」→ 文案**永久错位**：乐观翻转 + `let _ = send_control(...)` 吞错，
   校正依赖下一帧快照（离线时没有）；且 `pipe.rs::read_session` 开头 `File::open(PIPE_PATH)?`
   用 `?` 提前返回，**跳过了函数末尾的 `sync_tray_pause(app,false)`**，连断线复位都走不到。
3. `TrayPause` 只存了菜单项句柄，没存 `TrayIcon` 句柄 → 想更新 tooltip/icon 都没有入口；
   功能清单 §87 要求的「托盘图标可切实时速率模式」从未实现。
4. 菜单缺「开机自启」（功能清单 §87 列了 5 项，实现 4 项；settings 里有 get/set_autostart）。
5. **无单实例**（Cargo.toml 没有 tauri-plugin-single-instance）→ 多开会各建一个托盘图标，
   第二个实例连不上采集管道（`maxNumberOfServerInstances:1`），它的托盘永远停在「暂停监控」。
6. `TrayPause.item` 注册竞态：`pipe::spawn()` 早于 `item` 赋值，若首帧即 paused，

## §36 进程表排序三态：补上「取消排序」（用户反馈）

用户原话：「点击完排序之后就没有地方可以取消排序了，比如说点了应用或者下载，上传」。
根因不是显示问题，是**状态集合缺一项** —— `sortKey` 只有列名，没有「没排」这个取值。

### 定下来的口径

- `sortKey` 增加空串 = 未排序；`nextSortState(key, curKey, curDir)` 三态循环：
  别的列 → 该列首选方向（只有「应用」是文本→升序，其余五列降序）；同列 → 反向；再同列 → **取消回默认**。
- 空 `sortKey` 时 `visibleProcesses` **仍要排序**，走 `DEFAULT_SORT = { key:'download', dir:-1 }`。
  直接跳过 sort 会把采集端顺序端上来，默认视图每秒乱抖一次。
- 默认态表头**不标箭头**（`index.html` 里写死的 `is-sorted`/`aria-sort=descending` 要去掉）：
  否则「取消排序」和「按下载降序」视觉上是同一个东西。
- 「下载」列从默认态点第一下行序不动（默认本就是下载降序），只多出箭头 —— 这是对的，不是死点击。
- 表外出口：卡片头 `.icon-btn.sort-reset`（28px 与搜索框同高），排序生效才 `hidden=false`，
  一步复位行序/箭头/按钮三样。

### 踩到/顺手补的两处

- `is-sorted` 此前**没有任何 CSS 规则**，`classList.toggle` 挂的是个死钩子（箭头跟目标列同为
  `text-3`，点了看不出哪列在排）。补 `color: var(--text)`；不上 `--down/--up`（上传列戴下载色是错的）。

## 启动动效第二版：缩小居中 + 时间线重排 + 单实例守卫

用户三件事：①「动画可以小一点放中心」②「死快死快的，上网查人家的设计案例来模仿」
③「npm run dev 为什么会启动两个窗口」。

### ③ 双窗口根因（先查后改，证据确凿）

**不是 tauri 的行为，是没有单实例守卫。** 实测 `tasklist` 同时列出 **3 个独立
`netpeek-app.exe`**（PID 26408/18756/7196，各自有主窗与托盘图标）——
WebView2 的子进程叫 `msedgewebview2.exe`，所以这三个是三个应用实例。
叠加「主窗关闭只是 hide 到托盘、进程不退」，于是「再点一次图标 / 再跑一次 dev」
不会唤出旧窗口，而是长出第二个。

**修法**：`tauri-plugin-single-instance = "2"`（落 2.4.4），
**注册在插件链第一位**，回调里复用 `show_main(app)`（带 unminimize+set_focus+广播）。
顺序有讲究：它拦的正是「第二进程启动」，排后面的插件在注定退出的进程里会白跑一遍 init。
**验证**：清空存量后连开三次，进程数始终 1；第二/三次秒退（退出码 0）；
进程窗口类名出现过 `com.netpeek.app-siw`（siw = single instance window）作为副证。

**排查手法可复用**：本机 PowerShell 工具在此环境**完全无 stdout**（`(Get-Process).Count` 都没输出），
查进程一律走 bash 的 `tasklist`（带 `MSYS_NO_PATHCONV=1`）；
`tasklist /V /FO CSV` 能同时拿到 PID / 内存 / 窗口标题，判断「几个实例」够用。

### ① 版式缩小 + 真居中

`compose_lockup.py`：`MARK_W` 560 → **400**（占窗宽 47%→34%），字标与间距改为
比例派生（`WORD_RATIO=0.90`、`GAP_RATIO=0.14` → 360 / 56）。
删掉硬编码 `MARK_TOP=117`（那是「上 117 下 146」，比真居中高 14.4px），
改为 `mark_top = (VIEW_H - block_h)/2` → 上下边距都 196.6。
**独立发现的坑**：lockup 是**上下堆叠**（波形在上、字标在下），我一度按左右排去理解，
算错过一次 `margin_x`；看图形/截图之前不要凭代码印象判断版式结构。

### ② 「死快」的四条成因（逐条可量，不是「时长乘二」）

1. **扫速**：主波 560/620 = 0.90 px/ms、字标 504/400 = **1.26 px/ms** → 降到 0.42 / 0.58。
   （标记缩到 400 但时长加长，两头一起贡献）
2. **缓动方向错**：`.25,.7,.35,1` 是**减速**曲线，前 30% 时长走完约 50% 路程，
   **起手是弹出去的** —— 这才是「快」的主因。换成 `cubic-bezier(.42,0,.58,1)` ease-in-out。
3. **零定格**：原先字标 1330 擦完、1400 就卸幕，只隔 70ms；人眼要 200~400ms 登记。
   → 补 **400ms 定格**（`ANIM=2000` + `HOLD=400`，在 boot.js 里拆成两个常量，
   这样「为什么要等这么久」有答案、下次知道该动哪一段）。
4. **相位差太挤**：三条线间距 80/240 → **140/420ms**，才读得出先后。

缓动改为不再自编，直接用 **Material 3 motion token**（decel 进场 / ease-in-out 描线 /
accel 退场）。退场也从「260ms 把内容和幕布一起淡掉」改成两段式
（内容缩到 97.2% 淡出 220ms，幕布晚 100ms 起、360ms 揭开）。

外部参照（查到的，不是猜的）：Android 官方 splash ≤1000ms（手机，启动页在挡操作）；
通用 logo 动效指南给 splash = 2–3s「品牌时刻」；桌面端窗口已算出来更接近后者，2400ms 落在区间内。
描线缓动的主流做法（CSS 教程 / anime.js / GSAP 的 path drawing 示例）一致是 ease-in-out 类而非 ease-out。

### 同步改掉的工具常量（漏改不报错、只出错数）

- `qa_motion.py` 三个 y 波段按 ×0.714 重算：`MARK_BAND(188,330)` / `ECHO_BAND(331,400)` /
  `WORD_BAND(440,534)`。**忘了改的表现不是报错**，而是带子切到别的元素，
  要到 F 断言（字标墨迹宽）才红。

## 启动窗口居中（用户报「偏右下」）

**根因**：`tauri.conf.json` 的 main 窗口从没指定过位置（没 `center`、没 `x/y`），
tao 于是把 `(CW_USEDEFAULT, CW_USEDEFAULT)` 交给 `CreateWindowExW`
（`tao-0.35.3/src/platform_impl/windows/window.rs:1204`），位置交给 Windows 的默认落点。

**本机实测（1920×1200 @150%，逻辑 1280×800；任务栏自动隐藏 → 工作区 = 整屏）**：
主窗物理 1770×1080（=1180×720 逻辑 ×1.5），实际左上角 **(82, 75)**，
居中应为 **(75, 60)** → **Δ=(+7, +15)**；四边留白 左82/右68/上75/下45。
用户说「偏右下」是准确的（右、下留白更小）。

**修法**：`tauri.conf.json` main 窗口加 `"center": true`。走
`tauri-runtime-wry-2.11.4/src/lib.rs:4535` 起的创建期计算：
`primary_monitor()` 的 **work_area** 减去窗口尺寸再除二，位置在创建时就写死。
`decorations:true` 才会把 Windows 阴影宽度补进宽度（`AdjustWindowRect`）；
本窗 `decorations:false + shadow:false` → 补偿 0、内框即外框，算式精确。

**验证**：新增 `assets/boot-motion/tools/check_window_center.py`（ctypes 直调 user32，
量窗口矩形 / 显示器 / 工作区三组数）。冷启动**两次都是 (75,60)、Δ=0、四边两两相等**。

**三个坑（都在这个任务里踩到）**：
1. **主窗类名是 `Tauri Window`**，不是 `com.netpeek.app`；tauri 用系统通用窗口类，
   主窗和迷你窗同类名，只能按**标题**找。带标识的 `com.netpeek.app-sic`（标题
   `com.netpeek.app-siw`）是单实例插件的 22×22 消息窗 —— 之前记的「窗口类名
   `com.netpeek.app-siw` 是守卫副证」说法要按这条修正：它是**标题**、类名是 -sic。
2. **本机 PowerShell `Add-Type` 被安全策略拦**（"Add-Type compiles and loads .NET
   code at runtime"），`[System.Windows.Forms.Screen]` 这类写法全废 → 用 Python ctypes。
3. **`GetWindowRect` 对最小化窗口返回 (-32000,-32000) 哨兵值**（不是位置），
   不判 `IsIconic` 就会算出「偏了 32841 像素」；且用 ctypes 前必须先
   `SetProcessDpiAwarenessContext(-4)`（PER_MONITOR_AWARE_V2），否则拿到虚拟化坐标
   与物理坐标不同源，出假阳性。**隐藏窗口（托盘态）的矩形是有效的，照量。**

**构建期插曲**：`cargo build` 报 `LNK1104: cannot open file ...deps\netpeek_app.exe`
= 产物被占用。原因：`target/debug/netpeek-app.exe` 与 `target/debug/deps/netpeek_app.exe`
是**硬链接**（link count 2，`ls -la` 第二列能看出来），运行中的实例会同时锁住两个路径。
用户当时在跑 `npm run dev`（cargo 也持有 build 目录锁，所以先出现
`Blocking waiting for file lock on build directory`）。**tauri dev 会监视
tauri.conf.json 并自动重建**，实测配置 17:04:14 改、产物 17:04:52 就绪。

**开发时副作用（已记进 §39.4）**：有守卫之后，旧实例还活着时再跑 `npm run dev`，
新进程被拦掉、只把旧窗口唤到前台 —— 表现为「dev 起来了却没窗口」。
先 `taskkill /F /IM netpeek-app.exe` 再跑。

## 41. 重连首帧假速率：Y 轴的「尖峰」不是量程算法的问题（已修，待真机复验）

用户问「实时带宽的 Y 轴有问题吗，比如说突然到 50MB 了」。**结论：Y 轴量程算法没坏，
是采集端在 UI 重连时报了一个假速率。**

**排除项（都量过，别再怀疑）**：
- 量程 = `niceMax(60 帧窗内最大值 × 1.06)`，取 1/1.5/2/…/10 整刻度。取的是**窗内最大值**，
  天然平滑：五种常态流量各 600 帧，量程变化的帧占比 0%–1.5%，只有「视频+偶发加载」
  有 8× 跳变且全部来自页面加载那一下。**不是「抖轴」**。
- 轴标注宽度不会撑开 y 轴槽：「80 KB/s」与「60 MB/s」等宽，实测 `grid.left` 两档都 56px。

**真缺陷（实测）**：`EtwSnapshotSource.GetSnapshot()` 里 `downDelta = DownloadTotal - LastDownloadTotal`，
而 `LastDownloadTotal` **只在 GetSnapshot 被调用时推进 = 只有 UI 连着时才推进**。
断开期间 ETW 照收、累计值照涨，基线冻着 → 重连首帧把整段存量当成 1 秒增量报出。
直读 `\\.\pipe\NetPeekCollector` 实测：首帧 **137.09 MB/s**（复验 152.78），第 2 帧 10.70 KB/s，
**差 1.3 万倍**。触发极其日常：采集端是常驻提权进程，UI 每重启一次就是一次重连。

**打坏三处**：① 图表量程被顶到 150 MB/s 锁死 60 秒，常态流量压成绘图区 **0.1%** 的贴底直线
（真机 ECharts 实测：80 KB/s 量程下常态占 75% → 60 MB/s 量程下占 0.1%，一帧 750× 跳变）；
② **历史库被写进假流量** —— 按分钟汇总，09-12 17:09 是 1933 MB（占当天 55%）、
09-14 16:33 是 1460 MB（占当天 44%），而全部分钟中位数只有 2.1 MB；
指纹是「上下行几乎相等」（0.95 / 0.91）且 110 个进程行几乎每行都有一笔。
**这两天的「今日」合计、30 天柱图、历史屏都被灌了 44%–55% 的假数据，未清理，等用户定。**
③ 网速提醒（pipe.rs `check_rate_alerts` 只看单帧）会被误触发并吃掉 5 分钟冷却。

**修法**：`ISnapshotSource` 新增 `ResetRateBaseline()`，与既有 `ResetIconStream()` 同处同调
（图标早就处理过「连接边界」，速率的存量基线漏了）。只置 `_rateBaselinePending` 标志、
不跨线程改 `LastDownloadTotal`；标志**只在非 paused 分支消费**，换来不变量
「第一个真正报速率的帧必定是基线帧」；早返回（starting/error）也不消费，
所以「ServeAsync 之前调用」是安全的。副作用：重连后有 1 秒 `0 B/s`（计入今日/历史加 0，无害）。

**复验**：`scripts/verify-first-frame.mjs`（只读管道，自校准判据 `首帧 ≤ 灌入量/5`，
拿不到网络时降级成绝对判据 1 MB/s）。修前实测退出码 1。
**需要用户跑 `pwsh -File scripts\dev-collector.ps1` 用新构建重启采集端（弹一次 UAC）后才能复验** ——
本机沙箱无法提权，也没法自己重启那个提权进程（不要 taskkill，否则用户手上没有可用采集端）。

**残留（等用户定，别顺手改）**：真尖峰仍会占满量程 60 秒。这是「线性轴必须装下峰值」的必然结果，
而那个峰值往往正是这一分钟最重要的信息。要去掉得先定产品口径（分位数上限+溢出标记 / 对数轴 /
裁掉加标注），`docs/开发进度.md` §41.7 列了三条的代价。

**顺带修**：`scripts/dev-collector.ps1` 原来**先构建后停止**，改过采集端后必以
`MSB3021/MSB3027 文件被 NetPeek.Collector (pid) 锁定` 失败（没改动时 MSBuild 跳过拷贝，
所以看起来像偶发）。已把 `Stop-Collector` 提到构建之前。

**排查手法**：Python `sqlite3` 以 `mode=ro` 读 `history.db`（WAL 不用 checkpoint，
只读打开即可）；Python/Node 直读命名管道绕过 UI；`dotnet build` 时若报产物被锁，
用 `-c Release` 出另一份产物验证编译（Debug 的 exe 被运行中实例锁着）。

## §42 启动动效窗口期该提前做什么（用户提问，已排查+写文档，改代码待定）

**用户问题**：「在进入程序播放动画的时候，程序是否应该提前处理一些东西」。

**结论**：该提前做的不是「预热缓存」，而是「把数据通路接通并消化掉前几帧」。
而且先要纠正假设 —— 那 2.4 秒不是「等待」是**预算**，还有 ~730ms 用不掉，
**所以这件事根本不是性能问题，是状态问题**。

**怎么量出来的**：新增 `scripts/boot-trace.mjs`（mock `__TAURI__` + 三档模拟 IPC 延迟）。
关键认识：**串行/并行是结构问题、与延迟无关**，所以结论不依赖对延迟的猜测；
三档只是用来证明「结论不随延迟变」。

| IPC 模拟延迟 | 幕布摘掉 | 动效下限 | 动效后富余 | 启动链总用量 | 占预算 | 两个查库串行占用 |
|---|---|---|---|---|---|---|
| fast 20/80ms | 3162 ms | 2400 ms | 762 ms | ~0.38 s | 16% | 21.9 ms |
| mid 60/240ms | 3116 ms | 2400 ms | 716 ms | ~0.67 s | 28% | 65.9 ms |
| slow 180/900ms | 3134 ms | 2400 ms | 734 ms | ~1.63 s | 68% | 185.7 ms |

幕布时刻三档几乎不动（3.12–3.16s）→ `boot.js` 判定是 `elapsed()>=2400 && appReady`，
启动链最慢 1.63s 也落在预算内。**把启动链并行化现在是无收益优化**（省 44–66ms = 2–3%，用户看不到）。
⚠ **但慢档已占 68%**：富余不是用来「再加活」的，是吸收慢机器的余量；一旦顶穿 2400ms，
幕布会被 `AFTER_ANIM` 拖到 4.0s 才摘，而这正是启动层要避免的「让用户等」。
若真要动，**优先级是「设置屏 6 个 IPC 挪到进屏再取」而不是「两个查库并行」** ——
前者是启动时 100% 用不到的数据（初始屏硬编码 `let screen='live'`，`main.js:78`，无持久化），
是「去掉一件本不该在这里的事」；后者首绘就要用，只是可并行。

**真正的问题（42.3）**：三段代码拼出来的丢帧。
1. `SnapshotPipeServer.cs:55-57` `produceSnapshot()` 在 `Task.Delay` **之前** → **连上立即推首帧**，不等 1 秒。
2. `CollectorService.cs:44-45` + `EtwSnapshotSource.cs:439-449`：每次 `ServeAsync` 前清空已发图标集合，图标只对「集合里没有的路径」下发 → **首帧是唯一带全量图标的帧**（§29 记过约 143KB）。
3. `lib.rs:328` `pipe::spawn` 在 `setup` 里就连管道，而前端要等 WebView 解析完 13 个脚本（含 ~1MB ECharts）才登记 `listen('snapshot')`。
Tauri 事件即发即弃、不缓冲 → **首帧（全量图标帧）丢在 WebView 还没跑 JS 的那段**。
- 速率不受影响（41.3 让首帧是 0 值基线帧，且 `LastDownloadTotal` 已在采集端推进）。
- **图标受影响**：`main.js:92-96` `iconCache` 只从 `IconUpdates` 填充、**无补发机制** → 整会话首字母占位牌，直到下次管道重连。
- §29 的「未动」条目早就把这件事留成待办（"另算一件事"），本次就是那件事。
- **诚实标注**：三条代码事实确定；「首帧确实发在登记监听之前」是**推断**（本机沙箱没实测，
  当时应用与采集端都没在运行）。一分钟确认法：采集端保持运行，退出重开界面，看是否首字母占位牌。

**已排除（42.4）**：`show` 与 `listen` 的先后**没问题** —— 监听稳定早于显示 31–63ms，
靠的是 `reveal()` 里两层 `rAF` 把 `show()` 推迟两帧。但余量薄（31–63ms），
且量的是「登记时刻」不是「完成时刻」，真机 `listen` 是真实 IPC 往返 → 断言里留了 <10ms 告警。

## §42 落地：反向握手 + 231 区分（用户拍板「走 A，顺带做」，19:30）

  .catch 兜底——信号是通知不是请求）。信号幂等：页面重载再发无副作用。

  离线屏「未连接」对两种成因都字面为真，UI 从不显示错误原文，日志才是诊断面。
- **诚实记录的行为变化**：采集服务未启动时首条日志最多晚 10s（等兜底）；正常路径
